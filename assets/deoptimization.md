# V8 deoptimization reasons: meanings and responses

This guide covers the reason names and messages in V8's [`deoptimize-reason.h`](https://github.com/v8/v8/blob/73f16b50/src/deoptimizer/deoptimize-reason.h) at commit `73f16b50`: 68 regular reasons and 16 lazy reasons. V8 can add, remove, or rename them, and the exact reason selected for a program depends on its V8 version, compiler tier, warmup, and runtime feedback.

V8 optimizes using observations and assumptions about values, object shapes, and call targets. A deoptimization lets execution continue correctly when an assumption or dependency no longer holds. A deopt is not by itself a bug or a performance problem. First check whether it repeats in a hot function and whether a profile shows a real cost. Examples below illustrate relevant patterns; they are not guaranteed to trigger the named reason. Source-level explanations for internal reason names are necessarily approximate. See V8's [Maglev overview](https://v8.dev/blog/maglev) and [hidden class documentation](https://v8.dev/docs/hidden-classes).

In the tables, `—` means there is no useful or reliable second/third example. “No direct fix” is a valid response for normal tiering or an engine-internal event.

## Lazy deoptimization reasons

Lazy deoptimization commonly invalidates optimized code that depended on runtime state, such as object maps, prototypes, or constant-like fields. These events are often correct and expected. See V8's [lazy unlinking overview](https://v8.dev/blog/lazy-unlinking) and the source definitions above. Examples are illustrative and generally cannot guarantee the exact V8 reason.

| V8 reason | Message | Meaning / typical trigger | Example 1 | Example 2 | Example 3 | Practical response |
|---|---|---|---|---|---|---|
| `MapDeprecated` | dependent map was deprecated | A map-transition tree was deprecated; optimized code registered on the transition dependency group was marked for deoptimization. Different object shapes alone do not imply map deprecation. | — (map-deprecation transition is engine-managed; no reliable short JS trigger) | — | — | Usually no action. Inspect map transitions only if repeated deopts are measurable. |
| `PrototypeChange` | dependent prototype chain changed | A prototype used by optimized code was replaced or its chain changed. | `function read(o) { return o.x }` then `Object.setPrototypeOf(o, p)` | `Object.setPrototypeOf(C.prototype, otherProto)` after hot use | — | Avoid runtime prototype mutation, especially in hot paths. Set prototypes during initialization. |
| `PropertyCellChange` | dependent property cell changed | A V8 global PropertyCell changed in a way that invalidated compiled dependencies, such as a relevant value/constness transition or protector invalidation. | `globalThis.limit = 10; function f(x) { return x < globalThis.limit }` then update `globalThis.limit` (illustrative only) | — | — | Often normal. If costly and frequent, pass changing values explicitly; verify that the binding is actually a PropertyCell in this runtime. |
| `FieldTypeConstChange` | dependent field type constness changed | A property assumed constant by optimized code was written with a different value. | `const o = { x: 1 }; function f() { return o.x }` then `o.x = 2` | — | — | Keep intended invariants stable or represent mutable state separately. Change only if repeated and measurable. |
| `FieldTypeChange` | dependent field type changed | A property's observed type changed, invalidating a field-type dependency. | `const o = { x: 1 }; function f() { return o.x + 1 }` then `o.x = "s"` | — | — | Keep hot fields' types stable when natural; normalize values or separate representations if profiling shows recurring cost. |
| `FieldRepresentationChange` | dependent field representation changed | A field's internal representation changed, for example from integer-like to double or tagged. | `const o = { x: 1 }; function f() { return o.x + 1 }` then `o.x = 1.5` | Then assign `o.x = "s"` | — | Avoid mixing representations for the same hot property where practical; use separate fields/objects if this reflects distinct data. |
| `InitialMapChange` | dependent initial map changed | A constructor's initial map was replaced/changed, invalidating code that depended on that initial map. Adding a field to an instance does not automatically do this. | A constructor/prototype initial-map replacement after optimized allocation feedback (engine-managed; no short deterministic repro) | — | — | Keep initialization/prototype setup before hot use. ## Reading the examples

- Snippets show plausible inputs or mutations associated with a reason family. V8 chooses a specific guard and reason at runtime, so a snippet may produce a different reason or no deopt at all.
- Many `InsufficientTypeFeedback...` reasons concern compiler feedback or tiering, not a defect in the source operation. A warm-up run is not automatically a useful fix.
- Shape/type stability can help measured hot paths, but JavaScript permits mixed values and changing objects. Preserve semantics; optimize only after profiling.
- OSR, debugger, testing, GC, and frame-materialization reasons may be normal engine events or internal diagnostics. They often have no application-level fix.

## Source audit and verification

I checked these entries against the shallow V8 source checkout at commit [`73f16b50`](https://github.com/v8/v8/tree/73f16b50). The reason names/messages are declared in [`deoptimize-reason.h`](https://github.com/v8/v8/blob/73f16b50/src/deoptimizer/deoptimize-reason.h). The logging path writes both eager deopts and dependency invalidations as `code-deopt` records with the reason text in the final field ([`log.cc`](https://github.com/v8/v8/blob/73f16b50/src/logging/log.cc#L1716-L1758)).

Deoptigate does not maintain a whitelist of reason names: it stores the final field as `deoptReason`. Lazy invalidations use the bailout kind `dependency-change`, which is now assigned lazy severity by the parser so the UI can classify them. The regression test [`deopt-reasons.test.js`](../test/deopt-reasons.test.js) synthesizes a correctly shaped modern V8 record for every one of the 84 catalog messages and checks that deoptigate preserves each message and assigns eager/lazy severity correctly.

That is a **parser coverage test**, not proof that a JavaScript snippet causes every reason. V8's own exact reason-string tests are sparse. In this checkout, direct reason assertions include `NotANumber` in a Wasm-wrapper test, `WrongCallTarget` in Wasm tests, `NotASmi`/`NotAHeapNumber` and `LostPrecisionOrNaN` in CPU-profiler tests (some accept alternatives), `Testing`/`Unknown` in FileCheck tests, and lazy `ContextCellChange`/`Testing` traces. Many other V8 tests exercise a guard or deoptimization behavior without asserting the exact reason string. The current source enum has 68 regular and 16 lazy reasons; it does not contain `AllocationSiteTenuringChange`.

[`deopt-cases.test.js`](../test/deopt-cases.test.js) runs cases in separate Node processes with `--log-deopt`, parses real V8 logs with `processLogContent`, and checks the expected symbolic ID. Before running a case, it filters IDs absent from the lookup for the active V8 major. The lookup is generated from the earliest tags `8.0.1` through `15.0.1`. With that prefilter, Node 20 (V8 11.3) previously matched 27 cases, failed 13 reproducibility checks, and filtered 44 IDs absent from `11.0.1`; the `InstanceMigrationFailed` case is now verified there as well. Node 22 (V8 12.4) matches 33 exact IDs, detects nine Maglev-only paths as unavailable because this binary was built with Maglev disabled, detects V8 12's `ConstTrackingLet` behavior for the `WrongValue` case, and passes 112/112 assertions; it filters 41 IDs absent from `12.0.1`, with no TAP skips. Node 24 (V8 13.6) matches all 45 available IDs and passes 136/136 assertions, filtering 39 IDs absent from `13.0.1`. Node 27 (V8 15.6) matches 67 exact IDs, detects two source-confirmed non-loggable/build-limited cases, and passes 208/208 assertions; it filters 15 IDs absent from `15.0.1`. The test detects the `NotANumberOrUndefined` build fallback from its exact `NotANumber` log and the `EagerDeopt` log suppression from its exact initiating `NotASmi` event. A required flag is also detected before running its case. The runner does not open the browser UI and adapts manual optimization preparation to the active V8. It prints observed reason IDs, raw messages, and exit codes for failures. Regenerate the lookup with `node test/generate-deopt-reason-aliases.js`; it fetches the headers directly from GitHub. A cached header directory can be supplied as the first argument for offline regeneration. One ambiguity exists in V8 `10.0.1`: `dynamic check maps failed` maps to both `DynamicCheckMaps` and `DynamicCheckMapsInlined`; the lookup preserves both IDs, but the log message alone cannot distinguish them. The `ArrayBufferWasDetached` message differs by V8 version (`array buffer was detached` on V8 11/13, `array buffer was detached or immutable` on V8 14/15), so the test maps both to the same ID.
